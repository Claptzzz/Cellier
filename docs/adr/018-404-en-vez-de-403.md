# ADR 018 — Un hogar ajeno responde 404, nunca 403

- **Estado:** aceptada
- **Fecha:** 2026-10-01
- **Ámbito:** `HouseholdAccessService`, todos los controladores con `{householdId}`

## Contexto

Toda ruta con `{householdId}` necesita decidir qué devolver cuando el usuario autenticado no
es miembro de ese hogar. Hay dos respuestas posibles con semántica HTTP distinta: `403
Forbidden` ("existe, pero no tienes permiso") o `404 Not Found` ("no hay nada ahí para ti").

Usar `403` de forma consistente confirmaría, sin querer, que un `householdId` cualquiera
corresponde a un hogar real: probando identificadores al azar (o secuenciales, si no fueran
UUID) se podría enumerar cuáles existen con sólo mirar qué código devuelve cada uno.

## Decisión

**Un hogar al que el usuario no pertenece responde siempre `404`, exista o no.** La API no
confirma ni niega la existencia de hogares ajenos. El `403` queda reservado para el caso en que
el usuario **sí** es miembro del hogar pero el recurso exige un rol que no tiene (por ejemplo,
`ADMIN` para gestionar miembros o regenerar el código de ingreso): ahí ya se sabe que el hogar
existe y que la persona pertenece a él, así que explicar por qué se rechaza la petición no
revela nada nuevo.

La comprobación vive en un único punto, `HouseholdAccessService.requireMember` /
`requireAdmin`, para que ningún controlador tenga que reimplementar la distinción.

## Consecuencias

1. **No se puede enumerar qué hogares existen** probando identificadores sin ser miembro de
   ninguno: todos responden igual, `404`.
2. **El frontend no puede distinguir "no existe" de "no es tuyo"** a partir del código de
   estado, y no lo necesita: en ambos casos la acción correcta de la interfaz es la misma
   (volver, o mostrar que el recurso no está disponible).
3. **El `403` se vuelve una señal fuerte y poco frecuente.** Al aparecer sólo cuando la
   membresía ya está confirmada, un `403` en los registros apunta directamente a un problema de
   rol, no a una fuga de membresía.
4. **Cada endpoint con `householdId` depende de pasar por el guardia correcto antes de tocar
   datos.** Un endpoint nuevo que consulte la base de datos sin pasar por
   `HouseholdAccessService` rompería la convención sin que ningún tipo lo impida; se confía en
   la revisión de código y en la cobertura de pruebas para detectarlo.
